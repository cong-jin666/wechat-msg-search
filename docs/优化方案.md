### 2.2 代码层的硬伤（会当场被指出）

#### ① SQL 注入（`近义词模型.py:30-33`）

```python
words_str = "','".join(result_list)
words_str = f"'{words_str}'"
cursor.execute(f"SELECT ... WHERE segmented_content LIKE '%{input_word}%' OR ...")
```

用户输入直接拼进 SQL。输入 `' OR 1=1 --` 即拖库。
**改法**：参数化查询，`?` 占位。

#### ② 近义词条件实际不生效（同文件 33 行）

`segmented_content IN ('词1','词2')` —— 该列是整句分词用空格连接的字符串（如 `今天 天气 不错`），永远不会等于单个词。**只有 `LIKE` 那一半在起作用，近义词扩展白做了**。

#### ③ N² 全表更新（`提取词模型.py:30`、`总结关键词模型.py:29`）

```python
UPDATE MSG SET segmented_content=? WHERE StrTalker=? AND StrContent=?
```

逐行 UPDATE，且 WHERE 条件无索引 → 每行一次全表扫描。10 万行消息约等于 10 万次扫描，从秒级劣化成小时级。
**改法**：`SELECT rowid, ...` 后用 `rowid` 定位，`executemany` + 单事务批量提交。

#### ④ 增量失效（`提取词模型.py:15-20`）

`ALTER TABLE ADD COLUMN` 若列已存在，直接 `print` 后跳过整段回填逻辑。**第二次运行永远不处理新消息**，新聊天记录不会进入检索。

#### ⑤ 异常兜底缺失（三个脚本的 `finally`）

`cursor` 在 `try` 外未初始化，若 `connect()` 抛错，`finally` 里 `cursor.close()` 会抛 `NameError`，真实错误被掩盖。

#### ⑥ 硬编码与不可复用

- 路径写死 `D:\VsCodeP\output`
- 文件名含中文与空格，无法 `import`，无法单测
- `提取词模型.py` / `总结关键词模型.py` 无 `if __name__ == "__main__"`，一旦被导入就执行全表扫描

#### ⑦ 依赖风险

`synonyms` 包 2017 年后基本停更，依赖老版本 scipy/numpy，**在 Python 3.11+ 上安装经常失败**。建议替换为 jieba + 自建近义词表，或 text2vec。

---

### 2.3 图片模块跑不通（`图片特征提取/`）

| 文件 | 问题 |
|---|---|
| `word_pic.py:49` | 未导入 `TfidfVectorizer` → `NameError` |
| `word_pic.py:51` | 文本特征维度（词表大小）与图片特征维度（2048）不匹配，`cosine_similarity` 直接报错 |
| `查找带描述的图片.py:48-49` | `data` 列表 `"image4.jpg: ..."` 后**缺逗号**，与 image5 拼成一个字符串 |
| `查找带描述的图片.py:31` | `vectorizer` 依赖模块级变量，函数不可独立调用 |
| `文本描述查找图片.py` | 同维度不匹配问题 |
| `hog/zipper/哈希` | 单图演示脚本，无集成价值 |

**结论**：图片检索这条线**技术上就不成立**——文本 TF-IDF 向量和 ResNet 图像向量不在同一语义空间，无法直接算余弦相似度。正确做法是 CLIP 这类图文对齐模型，或「图片→LLM 生成描述→文本检索」。如果时间有限，**建议直接砍掉这条线**，专注文本检索。

```
wechat-msg/
├── app/
│   ├── main.py                 # FastAPI 入口 + 静态文件托管

│   │   ├── ingest.py           # 解析入库（PyWxDump 接入点）
│   │   ├── segment.py          # 分词 + 关键词（原两个脚本）

│       ├── schema.sql          # MSG + FTS5 虚表 + 索引

│   └── src/{views,components,api}
```

## 四、关键改造代码

### 4.1 参数化 + 批量 + rowid

```python
rows = conn.execute("SELECT rowid, StrContent FROM MSG WHERE type = 1").fetchall()
updates = [(seg(c), rid) for rid, c in rows if c]
conn.executemany("UPDATE MSG SET segmented_content = ? WHERE rowid = ?", updates)
conn.commit()
```

### 4.2 增量处理

```python
# 不再依赖"列是否存在"判断，改为按数据状态驱动
rows = conn.execute(
    "SELECT rowid, StrContent FROM MSG WHERE type = 1 AND segmented_content IS NULL"
).fetchall()
```

### 4.3 FTS5 全文索引（替代 LIKE 全表扫描）

```sql
CREATE VIRTUAL TABLE IF NOT EXISTS msg_fts USING fts5(
    segmented,
    content='MSG',
    content_rowid='rowid',
    tokenize='unicode61'
);
INSERT INTO msg_fts(rowid, segmented) SELECT rowid, segmented_content FROM MSG;
```

查询：

```python
conn.execute(
    "SELECT m.StrTalker, m.StrContent FROM msg_fts f "
    "JOIN MSG m ON m.rowid = f.rowid WHERE msg_fts MATCH ? ORDER BY rank LIMIT 50",
    (" OR ".join(terms),)
)
```

jieba 分词结果以空格分隔，天然适配 `unicode61`，10 万行量级从数百毫秒降到个位数毫秒。

### 4.4 近义词扩展（修掉原逻辑）

```python
def expand(word: str) -> list[str]:
    words = [word]
    nearby = synonyms.nearby(word)
    if nearby:
        for w, score in zip(*nearby):
            if 0.7 <= score < 1:
                words.append(w)
    return words
# SQL 侧：每个词独立 MATCH，而不是 IN 整句
```

### 4.5 长任务模型（Web 化的关键）

```python
@router.post("/api/parse")
def start_parse(req: ParseReq, bg: BackgroundTasks):
    task_id = uuid4().hex
    TASKS[task_id] = {"status": "pending", "progress": 0}
    bg.add_task(run_parse, task_id, req.db_path)
    return {"task_id": task_id}

@router.get("/api/tasks/{task_id}")
def get_task(task_id: str):
    return TASKS.get(task_id, {"status": "not_found"})
```

**不要**在 HTTP 请求里同步跑完整解析——必然超时并阻塞事件循环。

## 七、隐私与合规（必须写进 README）

微信聊天记录属于高敏感个人信息。上 Web 之后：

1. 默认只处理本机导出的数据，**不做服务端持久化**；
2. 演示/开源场景一律使用脱敏或伪造样本；
3. README 明确声明数据流向与不收集承诺；
4. 如需多人使用，解析接口必须做身份校验与目录隔离。

面试被问到「这些数据存哪、谁能访问」时，能答出这四条，反而是加分项。
